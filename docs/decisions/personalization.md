# Решение: персонализация в два этапа

**Зафиксировано в документации проекта 5–6 ноября 2026.** Это архитектурное решение, не отметка о вводе функциональности в эксплуатацию.

## Этап 1 — явные предпочтения PostgreSQL

Владелец формулирует предпочтения и вручную вносит их в `owner_profile.preferences`. Оркестратору предоставляется **чтение**, но не право произвольно создавать/обновлять предпочтения. Отсутствие записи — **неизвестное предпочтение**, не отсутствие ограничений.

Поле `preference_value` хранится в JSONB. До заполнения нужно согласовать способ обозначения области и срока применимости. Изменение и удаление должны оставаться доступными владельцу. Отдельный диалоговый профиль и специальный workflow подтверждения откладываются.

## Этап 2 — personal_assistant + RAG

После создания personal_assistant владелец сам помещает персональную историю в его RAG. Персональный контекст возвращает **только релевантные сведения**, по возможности с источниками, датами и сроком применимости; полный архив оркестратору не передаётся.

```text
Актуальные подтверждённые предпочтения PostgreSQL + история RAG
    → personal_assistant → необходимый персональный контекст
    → оркестратор + независимые данные домашних агентов
    → рекомендации
```

При противоречиях предпочтение, явно заданное владельцем и актуальное для данной области, имеет приоритет; исторические высказывания требуют проверки. Не перезаписывать PostgreSQL без решения владельца. Перед переключением предусмотреть сценарные тесты, недоступность RAG и откат. Конкретные API, векторное хранилище и миграции пока не выбираются.
