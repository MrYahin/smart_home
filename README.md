# Smart Home

Многоагентная система умного дома на базе Home Assistant и n8n. Целевая архитектура: единый оркестратор и специализированные агенты подсистем. Реализация оркестратора не подтверждена.

Обновлено: 26 октября 2026 года.

## Правила работы — читать первым

Перед каждым сеансом разработки, в том числе с ИИ-ассистентом, прочитать [AGENTS.md](AGENTS.md). Коротко:

- **GitHub — решение пользователя.** Что, когда и как попадает в GitHub и в `main`, решает только пользователь. Ассистент не делает commit, push, ветки, PR и merge; он предлагает код, пользователь изучает и тестирует его, затем сам сохраняет в `main`.

## Текущий результат

- Агент электроэнергии получает текущий контекст и историю одного датчика из Home Assistant.
- Владелец подтвердил завершение рабочих проверок и переход к хранению документальных данных и тарифам. Независимый удалённый запуск ассистентом не выполнялся.
- На Debian в Docker запущен PostgreSQL 18, база smart_home. Подключение n8n настроено и проверено владельцем.
- Сеть smart-home-storage закреплена в Compose n8n с сохранением прежней сети.
- Для загрузки квитанций подготовлена гостевая SMB-папка utility-import. Открытие, запись и удаление из Windows проверены владельцем.
- Автоматический импорт PDF ещё не реализован. Подключение входной папки к контейнеру n8n — ближайший шаг.

Подробности: [STATUS.md](STATUS.md). Приоритеты: [PLAN.md](PLAN.md).

## Архитектура

```text
Чат / вызов workflow
  → Agent energy (Gemini + Simple Memory)
      ├─ HA Read energy context → текущие показатели
      └─ Energy History → HA_EnergyHistory → история

Отдельно: HA Read context → MCP GetLiveContext

Подготовленная инфраструктура:
Windows → SMB utility-import → входной каталог на Debian
n8n ↔ PostgreSQL / smart_home / energy

Планируемый импорт:
PDF → текст → структурированные данные → PostgreSQL
    → удаление PDF только после успешной записи
```

## Текущий контекст и история HA

Текущий контекст использует POST /api/template: power, energy, voltage, current; группировка areas → devices → readings. Сохраняются идентификаторы, исходное состояние, числовое значение, единица и временные поля. Нечисловое состояние не превращается в ноль; единицы автоматически не пересчитываются. Датчики без привязок выделяются отдельно.

Известные месячные счётчики: sensor.sockets_kitchen и sensor.sockets_bath. Их источники: sensor.sockets_kitchen_energy и sensor.sockets_bath_energy. Месячный и исходный счётчики не складываются; период накопления источников не установлен.

История принимает entity_id, start_time, end_time; один sensor за вызов, даты с часовым поясом, максимум 7 суток, конец не в будущем. Это ограничения workflow. Выполняются нормализация, сортировка и диагностика. completeness=not_verified нельзя трактовать как подтверждённую полноту.

Исходный проверенный пример: 212 записей кухонного счётчика за 24 октября 2026, крайние значения 29.44 и 31.55 kWh. Разница крайних значений сама по себе не является проверенным суточным расходом.

По сообщению владельца, доступна история примерно за последний месяц, долгосрочная статистика не сохраняется. Причина независимо не диагностирована.

## Границы хранения

Долгосрочное копирование показаний датчиков HA в PostgreSQL отложено по решению владельца. Таблицы energy.sensors и energy.readings не являются действующим архивом; сбор не запущен.

PostgreSQL предназначен на текущем этапе для документальных показаний счётчиков, расхода, применённых ставок, начислений и дальнейшего справочника тарифов с датами и расписанием зон. Supabase, Qdrant и RAG не входят в текущий объём работ.

## Согласованный импорт PDF

Один workflow для разбора и записи за два года. Без ручного подтверждения, поиска повторно импортированных файлов, проверок арифметики/полноты и сводного отчёта по пакету.

- Извлечь текст и разобрать поля.
- Записать все данные документа в одной транзакции.
- После успешной записи удалить исходный PDF из входной папки.
- При ошибке извлечения, разбора или записи зафиксировать ошибку и оставить PDF.
- Ошибку удаления после записи фиксировать отдельно: повторная обработка может вызвать дубли или конфликт.
- Ошибки PostgreSQL фиксировать вне этой БД, чтобы недоступность базы не мешала журналированию.
- Ограничения БД остаются. Конфликты не скрывать через ON CONFLICT DO NOTHING в автоматическом импорте.

Успех записи не подтверждает правильность распознавания. Оригиналы следует сохранять в отдельном архиве владельца. Workflow пока не создан.

## Тарифы и документы

Разделяем показания, расход и начисления; индивидуальное потребление и общее имущество; период квитанции и фактический интервал измерений. Неизвестная дата снятия показания остаётся NULL. Ставка из квитанции — применённая ставка документа, а не доказательство даты введения тарифа. Расписание зон и сроки действия требуют отдельных сведений.

## Дальнейшее развитие

Импорт PDF и тарифы → Energy — Calculate на JavaScript → прогнозы → предложения → регулярные отчёты → оркестратор и другие агенты. Расчёты должны учитывать единицы, покрытие, границы периодов и сбросы.

## Безопасность

Не публиковать пароли, значения токенов, оригиналы квитанций, лицевые счета и персональные документы. Гостевой SMB-доступ выбран владельцем для доверенной локальной сети; доступные папке файлы могут читать, изменять и удалять подключившиеся клиенты. Не публиковать SMB в интернет. На Windows разрешён гостевой вход; требование подписи SMB снималось в ходе настройки и снижает защиту клиента за пределами этой папки.

Ранее опубликованные экспорты сохраняют локальные адреса и служебные ссылки по согласованию владельца; отсутствие найденных токенов не является полным аудитом. Управление нагрузками и создание автоматизаций — после подтверждения. Исключение для импорта PDF и удаления успешно обработанного файла согласовано отдельно.
