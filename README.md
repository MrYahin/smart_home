# Smart Home

Многоагентная система умного дома на базе Home Assistant и n8n. Цель — экономить деньги без снижения комфорта и улучшать условия проживания.

## Правила работы — читать первым

Перед разработкой прочитать [AGENTS.md](AGENTS.md). Пользователь решает, что и когда публикуется. Запись ассистентом в GitHub допускается только по прямой просьбе на конкретное действие и после согласования изменений. Настройку n8n ведём пошагово: владелец сам создаёт и изменяет узлы по инструкциям.

## Персонализация: сейчас и позднее

Сейчас предпочтения явно задаёт владелец и вручную вносит в PostgreSQL. Ближайшая задача — начальное заполнение owner_profile.preferences и подключение чтения существующему оркестратору. Автоматическое выявление привычек и запись предпочтений из диалога, отдельный workflow подтверждений откладываются. Второй общий чат не создаём. Отсутствие записи означает неизвестное предпочтение; модель не должна самостоятельно менять профиль.

Таблица preferences содержит id, preference_key (UNIQUE), preference_value (JSONB), description, created_at. Представление области и срока в JSONB согласовать перед записью. Тестовый INSERT/SELECT workflow пропущен; начальное заполнение и использование записей рекомендациями ещё не подтверждены.

После создания personal_assistant владелец помещает исторические данные о себе в его RAG. Затем получение рекомендаций перестраивается:

```text
Актуальные предпочтения PostgreSQL + исторический RAG
  → personal_assistant → релевантный персональный контекст
  → оркестратор + данные домашних агентов → рекомендации
```

Это будущая архитектура, не работающая интеграция. PostgreSQL сохраняет актуальные явно заданные предпочтения; история их автоматически не заменяет. Контекст должен включать источники, даты и применимость, если известны. Противоречия уточняются у владельца; оркестратору не передаётся весь личный архив. Интерфейс, миграции и технология RAG отдельно не выбраны. Развитие домашней системы не приостанавливается до готовности personal_assistant.

## Действующая архитектура

```text
Чат n8n → My workflow
  ├─ Call 'Agent energy' → Agent energy
  │   ├─ HA Read energy context → электрические показатели
  │   └─ Energy History → HA_EnergyHistory → история датчиков
  └─ uk_agent → Агент УК
      └─ uk_receipt_context → УК — Контекст квитанций
          └─ PostgreSQL → сохранённый результат парсера

Windows → SMB → входная папка → n8n
  → PDF → текст → парсер → PostgreSQL → удаление конкретного PDF
```

HA Read context через MCP — отдельный workflow. В экспорте Webhook Алисы ведёт к фиксированному ответу, не к AI Agent.

## Разделение ответственности

- Агент УК — единственный профильный агент по всем квитанциям ЖКХ, включая электричество; помощник владельца, не представитель УК. Использует только сохранённые сведения; не выполняет платежи, обращения, изменение БД или управление устройствами.
- Энергетический агент — электрические данные HA: мощность, энергия, напряжение, ток, история и нагрузки. Не получает сведения квитанций напрямую, от УК или через оркестратор. Источник ставок для стоимости не согласован.
- Оркестратор разделяет смешанные запросы и сопоставляет независимые ответы только при совместимости периодов, единиц и охвата. Расход отдельных нагрузок HA не равен общему расходу квартиры.

Память: energy:ha:v2:<sessionId>, uk:v1:<sessionId>, orchestrator:uk-energy:v2:<sessionId>. Промпты и ключи не гарантируют техническую изоляцию и не удаляют старую память. Противоречивая оговорка PLAN.md о передаче квитанций устранена; разделение агентов не меняется.

## Ограничения данных и импорта

- HA: один sensor за вызов, максимум 7 суток; completeness=not_verified не доказывает полноту. Ранее сообщалось примерно о месяце истории. Долгосрочный архив сырых данных отложен. Месячные счётчики не складываются с исходными накопительными; нечисловое состояние не равно нулю.
- Контекст квитанций — весь сохранённый payload, не полный PDF. Полнота задолженности, аванса, оплат, сроков и прочих разделов не подтверждена; отсутствие поля и null не означают ноль.
- Показания, расход, начислено и к оплате различаются. Индивидуальное потребление, общее имущество и содержание жилья разделяются. Итоги и перерасчёты повторно не суммируются.
- Расчётный месяц не задаёт точный период потребления; применённая ставка не доказывает действующий тариф и расписание зон. Отдельный тарифный справочник не создаём; Т1–Т3 требуют официального подтверждения расписания.
- Статусы контекста: found, not_found, multiple_documents. Несколько документов не выбираются и не суммируются автоматически.
- Импорт остаётся без дедупликации, промежуточного подтверждения, автоматических арифметических проверок и сводного отчёта. Повторный импорт может создать дубль; ошибка удаления — оставить запись и PDF. Ошибка до записи не должна удалять файл.
- Успешный импорт не доказывает правильность парсинга или обоснованность начислений. Архив оригиналов и журнал ошибок вне PostgreSQL без отдельного решения не добавляем.

По готовности personal_assistant — отдельный переход на персональный контекст и RAG с проверкой и возможностью отката. Расчёты выполняем кодом, выгоду и окупаемость не выдумываем.

## Безопасность

Не публиковать токены, пароли, оригиналы квитанций, лицевые счета, ФИО, адреса, личный исторический архив и закреплённые персональные результаты. Экспорты содержат служебные идентификаторы и локальные ссылки; полного аудита безопасности нет.

SMB utility-import: /home/yaha/utility-import/incoming → /files/utility-import. Гостевой доступ — только доверенная локальная сеть; клиенты могут менять и удалять файлы. Не публиковать SMB в интернет. Изменения гостевого входа и SMB-подписи Windows имеют клиентский масштаб.

Execute Command расширяет полномочия workflow. Удалять только конкретный проверенный путь внутри входной папки; файловые ограничения n8n не являются песочницей shell. Удаление успешно импортированного PDF согласовано отдельно. Предпочтение не разрешает управление устройствами: покупки, ПО, оборудование, настройки, платежи, обращения и управление требуют отдельного подтверждения.
