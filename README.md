# Smart Home

Многоагентная система умного дома на базе **Home Assistant + n8n + PostgreSQL**.

**Стратегическая цель:** последовательно повышать комфорт, безопасность, надёжность и экономическую эффективность домашнего хозяйства. Оркестратор не только отвечает на вопросы, но и **анализирует наблюдения всех профильных агентов, предлагает полезные покупки, модернизацию существующих систем и будущие мероприятия**, а после реализации помогает проверять эффект.

> Перед любой разработкой обязательно прочитать [AGENTS.md](AGENTS.md). Все изменения оборудования и настроек, обращения, оформление и оплата покупок — только с надлежащим отдельным решением владельца.

## Интерфейс системы

**Принятое направление:** рекомендации и задачи показываются на существующих дашбордах **Home Assistant** с группировкой вкладок **по назначению**, а не обязательно по одному агенту. Чат n8n остаётся способом подробно обсудить решение с оркестратором; новую систему чатов или отдельный UI не создаём.

### Где показывать рекомендации

- **Главная вкладка:** отдельная карточка 1–3 наиболее значимых предложений **оркестратора** для всего дома (новые покупки, модернизация, обслуживание и дальнейшие активности). Не дублировать без необходимости все частные рекомендации.
- **Каждая существующая вкладка подсистемы:** своя карточка рекомендаций, относящихся к назначению вкладки. Вкладка может объединять наблюдения нескольких профильных агентов; конкретное соответствие определяем по реальным карточкам дашборда.
- Если полезных и подтверждённых рекомендаций нет, показываем «Новых рекомендаций нет», а не создаём совет ради заполнения карточки.
- Исходные YAML/конфигурации карточек, описания вкладок и их связи с агентами сохраняем по мере предоставления владельцем в [каталоге вкладок](docs/interface/tabs/README.md). Не менять дашборды HA только из-за размещения документации в GitHub.

### Хранение: Home Assistant Local To-do

Для первого этапа выбираем **штатную интеграцию Local To-do Home Assistant**, без отдельного PostgreSQL-реестра рекомендаций. Списки хранятся в локальных файлах HA (`.storage/local_todo.*.ics`), **не в Recorder**; обычная очистка истории Recorder не задаёт срок хранения этих задач.

- Предусмотреть отдельный список Local To-do для главной карточки оркестратора и списки для вкладок подсистем (точные `todo.*` entity_id определим по конфигурациям HA). Физическая группировка идёт по **вкладкам**, не по числу агентов.
- **Только два штатных состояния элемента:** `needs_action` и `completed`. Не вводить третьи статусы To-do.
- В описании элемента или согласованных метаданных хранить устойчивый идентификатор рекомендации, источник/агента, привязку к вкладке, дату создания, дату следующего рассмотрения, обоснование и ссылки на исходные наблюдения. Дату создания фиксировать отдельно: `due` предназначен для срока выполнения.
- Различие «рекомендация / принятая задача» и «пока не показывать» — **логика карточки и обработки элемента**, а не дополнительные статусы To-do. Формат метаданных согласуем при реализации.

### Действия с карточкой

| Действие | Логика |
| --- | --- |
| **В работу** | Зафиксировать выбор владельца, сделать рекомендацию задачей соответствующей подсистемы/агента; сохранить `needs_action` до реального выполнения. Само нажатие не разрешает покупку, платеж или управление устройством без отдельного согласования. |
| **Не сейчас** | Оставить `needs_action`, записать срок повторного рассмотрения и скрыть из текущей карточки до его наступления; показать следующую подходящую рекомендацию. Не удалять и не отмечать как выполненную. |
| **Подробнее** | Показать факты, источники, предполагаемую пользу, стоимость при наличии расчёта и альтернативы; при необходимости обсудить через существующий чат. |
| **Выполнено** | Только после подтверждённого выполнения установить `completed`; если возможно, зафиксировать результат проверки эффективности. |

Штатная карточка To-do отображает список и не реализует весь такой сценарий самостоятельно: выбор **одной приоритетной** рекомендации, фильтрация отложенных, кнопки и переход к следующей потребуют автоматизаций/шаблонов HA и связки с n8n. Возможности конкретной версии проверить перед внедрением; функции пока **не реализованы**.

### Генерация, сроки и очистка

1. n8n получает наблюдения профильных агентов и ежедневно формирует обоснованные предложения; оркестратор отбирает общедомовые приоритеты. Перед добавлением искать существующие совпадения по источнику, оборудованию и проблеме, чтобы не плодить дубликаты.
2. Новые элементы записываются в соответствующий Local To-do, а карточка на вкладке показывает актуальную подходящую рекомендацию. Новые карточки не должны заменять ранее принятые задачи.
3. **Целевой срок хранения — до 365 дней**. Local To-do не удаляет выборочно элементы по возрасту сам по себе: предусмотреть ежедневную очистку через HA/n8n. Удалять завершённые записи старше 365 дней и неактуальные отложенные записи после проверки; **активные незавершённые задачи не удалять автоматически только из-за возраста**.
4. Для фильтрации и очистки заранее фиксировать дату создания, решение владельца и срок пересмотра. Не применять массовое `todo.remove_completed_items` вместо выборочного удаления, если нужно сохранять годовую историю.
5. Проверить резервное копирование локальных файлов To-do, работоспособность операций `todo.get_items`, `todo.add_item`, `todo.update_item`, `todo.remove_item` в установленной версии и доступность нужных действий из выбранных карточек.

**Ограничения:** в общих дашбордах не раскрывать подробности лечения и другие чувствительные сведения; критические аварии безопасности не ждать до ежедневного обновления рекомендаций. Реализация, тесты и точные названия вкладок будут уточняться по переданным конфигурациям.

## Общая дорожная карта

Порядок работ и направления развития, а **не отчёт о выполнении**. Фактическая готовность — в [статусах](docs/status/README.md).

1. **Базовые данные и персонализация.** Вручную внести согласованные предпочтения в `owner_profile.preferences`, подключить чтение к оркестратору; не включать автоматическое изменение профиля. Проверить независимость энергетических данных HA и квитанций УК.
2. **Качество существующих подсистем.** Упорядочить энергетические датчики, историю и расчёты; расширить безопасный импорт квитанций за тепло, содержание жилья и интернет; сверить актуальные экспорты n8n с работающими версиями.
3. **Реестр дома и событий.** Подготовить перечень устройств, помещений, источников данных и базовых ограничений; начать с [агента сервиса](agents/service/README.md) и согласовать формат наблюдений для всех агентов.
4. **Климат и безопасность.** Развить [климат](agents/climate/README.md) и [безопасность](agents/security/README.md): выявлять отклонения, риски и возможности модернизации; проверять аварийные уведомления и качество данных прежде, чем включать управление.
5. **Новые профильные агенты.** По мере готовности исходных данных развивать [растения](agents/plants/README.md), [лекарства](agents/medications/README.md) и [автомобиль](agents/vehicle/README.md). Для медицинских сведений — отдельная защита и минимизация передачи; транспортную историю не дублировать без согласования с personal_assistant.
6. **Проактивный оркестратор (Home Improvement Planner).** Получать подтверждённые наблюдения профильных агентов, находить межагентные закономерности и готовить предложения **трёх типов: новое оборудование; модернизация действующих систем; предстоящие работы и активности**. Дедуплицировать предложения, ранжировать по безопасности, комфорту, эффекту, надёжности и сложности.
7. **Управление инициативами.** После отдельного согласования спроектировать реестр в PostgreSQL: проблема → предложение → решение владельца → план → выполнение → проверка результата. Отслеживать отклонённые, перенесённые и реализованные идеи, не повторять их без новых оснований.
8. **Периодические рекомендации.** Целевой цикл: 1–3 предложения ежедневно; еженедельный обзор проблем и работ; ежемесячный план затрат и модернизаций; ежеквартальная стратегия развития. Критические события безопасности требуют отдельного оперативного канала. Позже выводить сводку на существующий HA-дашборд.
9. **Подбор покупок.** [Агент закупок](agents/procurement/README.md) проверяет необходимые товары, совместимость, наличие, цену и доставку; формирует согласуемые корзины. Выбор приоритетов остаётся за оркестратором; заказ и оплата без отдельного подтверждения запрещены.
10. **Интеграция с personal_assistant.** После готовности сервиса использовать только релевантный исторический RAG совместно с явно актуальными предпочтениями PostgreSQL, с указанием происхождения и возможностью отката.
11. **Надёжность и безопасность.** Проработать резервное копирование с проверкой восстановления, диагностику отказов, журнал ошибок и минимальные права доступа. Реализацию и закупки выполнять только по согласованным этапам.

Предварительный порядок подключения новых агентов для обсуждения: **сервис → климат → безопасность → растения → лекарства → автомобиль → покупки**. Он корректируется по фактически доступным устройствам, пользе и рискам, не является утверждённым календарём.

**Принцип улучшений:** агент сообщает проверяемые факты и ограничения → оркестратор сопоставляет, оценивает и предлагает → владелец принимает решение → результат измеряется и влияет на дальнейшие рекомендации. Стоимость и окупаемость **не выдумываются**.
