# Smart Home

Многоагентная система умного дома на базе Home Assistant и n8n. Каждая подсистема получает собственного специализированного агента, а единый агент-оркестратор координирует их работу и формирует ответ пользователю.

Обновлено: 25 октября 2026 года.

## Цели

- Единый интерфейс общения с умным домом.
- Разделение ответственности между агентами подсистем.
- Проверяемые ответы на основе реальных показаний, истории и расчётов кодом.
- Развитие от мониторинга к аналитике, прогнозам и предложениям.
- Управление нагрузками и создание автоматизаций только после подтверждения пользователя.

## Текущий результат

Реализован базовый агент электроэнергии с двумя инструментами: текущие электрические показатели и история одного датчика за заданный период. Экспорты четырёх workflow находятся в репозитории.

Подключение истории проверено владельцем на одном счётчике и одном периоде: получено 212 записей и совпадающий ответ агента. Это не подтверждает полноту всей истории или готовность расчётов расхода. Независимый удалённый запуск n8n при анализе репозитория не выполнялся.

Подробности: [текущий статус](STATUS.md) и [актуальный план](PLAN.md).

## Архитектура

Целевая схема:

```text
Пользователь → Агент-оркестратор
                 ├─ Агент электроэнергии
                 └─ Другие агенты подсистем
```

Оркестратор выбирает исполнителей, передаёт контекст, объединяет результаты и запрашивает подтверждения действий. Его экспорт пока не предоставлен, поэтому реализация оркестратора не подтверждена.

Текущая конфигурация агента электроэнергии:

```text
Чат / вызов из другого workflow
  → Agent energy
      ├─ Google Gemini Chat Model
      ├─ Simple Memory
      ├─ HA Read energy context → текущие показатели
      └─ Energy History → HA_EnergyHistory → история

Отдельно: HA Read context → MCP / GetLiveContext
```

Home Assistant является источником показаний, истории и привязок к помещениям и устройствам. n8n выполняет запросы, проверку параметров и JavaScript-обработку. MCP не используется в цепочке электрических показателей, но отдельный MCP-workflow сохранён.

## Текущие электрические показатели

HA Read energy context использует POST /api/template и возвращает структуру:

```text
areas → devices → readings
```

Поддерживаются:

| Тип | Единицы |
|---|---|
| power | W, kW, Вт, кВт |
| energy | Wh, kWh, Вт·ч, кВт·ч |
| voltage | V, В |
| current | A, А |

Помещения настраиваются в Home Assistant через Areas. Сохраняются entity_id, device_id, названия, state, value, единицы и временные поля. Сущности без устройства попадают в unassigned своего помещения; без помещения — в группу «Без помещения».

Нечисловые статусы дают value: null, а не ноль. Единицы автоматически не пересчитываются. received_at — время формирования ответа; last_updated — время обновления состояния, не обязательно физического измерения.

### Известные месячные счётчики

| Помещение | За текущий месяц | Источник |
|---|---|---|
| Кухня | sensor.sockets_kitchen | sensor.sockets_kitchen_energy |
| Ванная | sensor.sockets_bath | sensor.sockets_bath_energy |

Назначение подтверждено владельцем. Месячный счётчик не складывается с исходным. Период накопления исходных счётчиков пока не установлен.

## История измерений

HA_EnergyHistory имеет ручной вход и вход из другого workflow.

Входные поля: entity_id, start_time, end_time. Начальная версия обрабатывает один sensor за вызов, требует даты с часовым поясом и ограничивает период семью сутками. Конец периода не может быть в будущем. Это ограничения workflow, а не самого HA.

```text
Ручной запуск → Test parameters ─┐
                               ├→ History parameters
Внешний вызов ──────────────────┘
    → HTTP Request
    → Normalize history
```

Результат содержит запрошенный период, число записей, единицы, временные границы, records и diagnostics. Проверяются нечисловые состояния, некорректные даты, единицы, выход за период и уменьшения соседних числовых значений. Уменьшение не объявляется автоматически доказанным сбросом. completeness остаётся not_verified.

### Проверенный пример

По данным владельца, sensor.sockets_kitchen_energy за 24 октября 2026, от 00:00 до 00:00 следующего дня, +03:00:

- 212 записей в kWh;
- первое показание 29.44, последнее 31.55;
- нечисловых значений, некорректных дат, пропущенных единиц и выхода за период не обнаружено;
- уменьшений между соседними числовыми записями не обнаружено;
- последняя запись за 671.381 секунды до конца периода;
- получен ответ агента с теми же числом записей и крайними показаниями.

Этот интервал до конца периода сам по себе не доказывает пропуск. Разница крайних значений не объявляется точным расходом за сутки без проверки границ, сбросов и полноты.

## На чём остановились

Базовое подключение истории выполнено. Ближайший шаг — закрепить проверки:

1. Запросить историю по понятному названию устройства: контекст → правильный исходный счётчик → история.
2. Проверить пустую историю, неверные параметры и превышение семи суток.
3. Проверить ещё один датчик и доступную глубину истории.
4. Уточнить промпт: убрать неподдержанное требование искать switch и явно сообщать о непроверенной полноте.
5. Сохранить безопасные тестовые примеры.

Остаются проверки доступа к чату, изоляции памяти по sessionId и прав вызова workflow.

## План развития

1. Закрепить текущий контекст и историю; завершить каталог расчётных измерений, покрытие квартиры и правила агрегации.
2. Подготовить историческое хранилище и тарифы с датами действия и зонами суток. Импорт PDF прошлых лет: извлечение → проверка → подтверждение → сохранение. RAG пока не нужен.
3. Создать Energy — Calculate на JavaScript: расход за период, стоимость, сравнения, обработка единиц, пропусков и сбросов; тесты на известных примерах.
4. Добавить простой прогноз до конца месяца с проверкой на прошлых периодах и указанием покрытия.
5. Создать Energy — Proposals: данные, гипотеза, необходимые проверки и ожидаемый эффект.
6. Настроить суточные и месячные отчёты, уведомления об отклонениях.
7. Развивать контракт специализированных агентов и единый оркестратор, подключать другие подсистемы.

Хранилище, тарифы, PDF-импорт, расчёт стоимости, прогнозы, предложения и регулярные отчёты не реализованы в предоставленных экспортax.

## Принципы безопасности и качества

- Только чтение в текущих инструментах агента энергии. Управление и автоматизации — после подтверждения.
- Не суммировать месячные и исходные счётчики, пересекающиеся группы и разные единицы без проверки.
- Не считать unavailable/unknown нулевым потреблением.
- Не прогнозировать всю квартиру по одной розетке и не выдумывать покрытие датчиков.
- Не публиковать значения токенов, пароли и персональные документы.
- В опубликованных экспортах сохранены локальный адрес HA, ссылки на credentials и служебные ID по согласованию с владельцем. Значения токенов в просмотренных полях не обнаружены; это не полный аудит безопасности.
- При каждом изменении реализации синхронизировать README.md, STATUS.md и PLAN.md.
