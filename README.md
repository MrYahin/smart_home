# Smart Home

Многоагентная система умного дома на базе Home Assistant и n8n. Обновлено: 30 октября 2026 года.

Перед разработкой прочитать [AGENTS.md](AGENTS.md). Пользователь решает, что и когда публикуется. Ассистент предлагает изменения; запись в GitHub допускается только по прямой просьбе пользователя на конкретное действие. Правила AGENTS.md этим обновлением не изменяются.

По сообщениям владельца и результатам, предоставленным в переписке:

- Агент электроэнергии получает текущий контекст и историю датчиков HA.
- PostgreSQL 18 работает в Docker на Debian: база smart_home, схема energy; подключение из n8n проверено. Сеть smart-home-storage сохранена вместе с прежней сетью n8n.
- SMB-папка utility-import подключена к контейнеру: /home/yaha/utility-import/incoming → /files/utility-import.
- Реализован последовательный импорт нескольких PDF: чтение → извлечение текста → локальный JavaScript-парсер → PostgreSQL → удаление PDF после успешной записи.
- Используются energy.utility_documents, energy.utility_meter_readings и energy.utility_charges. Полный результат парсера хранится в JSONB документа.
- Energy — Receipt Context подключён к агенту; получение ответа по квитанциям подтверждено владельцем.
- Причину сбоя повторного удаления владелец устранил; окончательное исправление не предоставлено в виде нового экспорта.

Прямые удалённые проверки Debian, n8n и PostgreSQL ассистентом не выполнялись. Полнота импорта двухлетнего архива, отсутствие отладочных дублей и корректность всех форматов квитанций не подтверждены. Работа импорта по расписанию отдельно не подтверждена.

Подробности: [STATUS.md](STATUS.md). План: [PLAN.md](PLAN.md).

## Работающая архитектура

```text
Чат / вызов workflow → Agent energy
  ├─ HA Read energy context → текущие показатели
  ├─ Energy History → HA_EnergyHistory → история
  └─ Energy — Receipt Context → PostgreSQL → квитанции

Windows → SMB → входная папка → n8n
  → PDF → текст → локальный парсер → PostgreSQL
  → удаление конкретного PDF после успешной записи
```

HA Read context через MCP остаётся отдельным workflow.

## Ограничения данных

- Текущий контекст группирует power, energy, voltage и current по помещениям и устройствам. Нечисловое состояние не считается нулём.
- История HA: один sensor за вызов, даты с часовым поясом, максимум 7 суток. completeness=not_verified не подтверждает полноту.
- sensor.sockets_kitchen и sensor.sockets_bath — месячные счётчики; не складывать их с источниками sensor.sockets_kitchen_energy и sensor.sockets_bath_energy.
- По прежнему сообщению владельца доступна история примерно за месяц; причина отсутствия долгосрочной статистики независимо не диагностирована. Архивирование сырых показаний HA в PostgreSQL не запускаем.
- Показания, расход и начисления разделяются. Индивидуальное потребление и общее имущество не смешиваются.
- Месяц квитанции не доказывает точные границы потребления. Неизвестная дата снятия остаётся NULL; предыдущие показания не восстанавливаются как документальный факт.
- Ставки квитанции — применённые ставки документа, а не доказательство актуального тарифа или срока его действия.

## Импорт PDF и хранение

Документ и связанные строки записываются одним SQL-запросом. Нет ручного подтверждения, дедупликации, содержательных автоматических проверок и сводного отчёта по пакету. Ошибка извлечения, разбора или записи останавливает процесс до удаления PDF. Ошибка удаления возникает уже после возможной фиксации данных; повторный импорт может создать дубль. Автоматические повторы записи не предусматриваются.

Успешная запись не гарантирует правильности распознавания. Исходные копии владелец хранит отдельно. Журнал ошибок вне PostgreSQL отложен.

Отдельный тарифный справочник не создаём. Ставки берём из квитанций; расписание Т1–Т3 при реализации аналитики сверяем с официальным источником и сохраняем небольшой конфигурацией с часовым поясом и источником. Для оценки текущего периода по прошлой квитанции явно указываем допущение.

## Новая цель: вечерняя аналитика и существующий дашборд HA

Для каждой получаемой энергетической сущности определить роль и связь с устройством или нагрузкой. Не считать мощность, энергию, ток и напряжение одного устройства независимыми потребителями.

Планируемая ежедневная цепочка:

```text
Вечерний запуск → история HA → расчёты по Т1 / Т2 / Т3
  → сводка и 1–3 обоснованные рекомендации
  → обновление существующего дашборда HA
```

Результат по нагрузке: время работы, расход и стоимость по зонам, итог, период, качество данных и время обновления. Различать включённое состояние и активное потребление. При недостатке данных не выдумывать значения или экономию. Точное вечернее время и границы периода ещё согласовать; для первой версии предложен текущий день до запуска.

Отдельный универсальный Energy — Calculate отложен; необходимые детерминированные расчёты входят в будущий процесс вечерней аналитики. Новый дашборд не создаём: сначала получить актуальную конфигурацию существующего и согласовать формат публикации. Старый результат при сбое не выдавать за свежий.

## Оркестратор

Оркестратор обязателен в целевой архитектуре: единый диалог, вызов профильных агентов, уточнения и объединение сведений разных подсистем. Пока реализован только энергетический специалист. Оркестратор ещё не создан; неподключённые системы не представлять работающими.

Расчёты остаются в профильных workflow. Вечернее обновление не зависит от чата. При необходимости агент запрашивает детали помимо готовых сводок. Реализацию первой версии оркестратора планируем после сквозной проверки одной нагрузки и дашборда; контракт закладываем заранее.

## Безопасность

Не публиковать токены, пароли, оригиналы квитанций, лицевые счета, ФИО, адреса и закреплённые персональные результаты. Гостевой SMB доступен только в доверенной локальной сети; подключившиеся клиенты могут менять и удалять файлы. Не публиковать SMB в интернет. Изменения гостевого входа и SMB-подписи Windows имеют клиентский масштаб.

Execute Command включён для удаления PDF и расширяет полномочия workflow. Удалять только конкретный проверенный путь внутри входной папки; файловое ограничение n8n не является песочницей shell-команд. Существующие экспорты с локальными адресами и служебными ссылками не считать прошедшими полный аудит.

Автоматическое удаление успешно импортированного PDF согласовано отдельно. Управление нагрузками не входит в текущую реализацию; прочие изменения внешнего состояния требуют согласования. Supabase, Qdrant и RAG сейчас не нужны.
