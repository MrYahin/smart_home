# Smart Home

Многоагентная система умного дома на базе Home Assistant и n8n. Цель — экономить деньги без снижения комфорта и улучшать условия проживания.

## Правила работы — читать первым

Перед разработкой прочитать [AGENTS.md](AGENTS.md). Пользователь решает, что и когда публикуется. Ассистент предлагает изменения; запись в GitHub допускается только по прямой просьбе пользователя на конкретное действие. Правила AGENTS.md этим обновлением не изменяются. Настройку n8n ведём пошагово: владелец сам создаёт и изменяет узлы по инструкциям.

## Текущее состояние — 2 ноября 2026

Основание — предоставленные экспорты и подтверждения владельца. После исправления SQL контекста квитанций владелец подтвердил работу новой связки; независимая удалённая проверка не проводилась.

- My workflow — оркестратор общего чата с двумя профильными агентами.
- Agent energy получает текущий электрический контекст и историю датчиков HA. Инструмент квитанций удалён, промпт ограничен данными HA.
- Агент УК получает сведения по всем услугам, сохранённым при импорте квитанций, через uk_receipt_context.
- Исходный Energy — Receipt Context переименован в УК — Контекст квитанций. Запрос возвращает весь payload из energy.utility_documents в receipts[].receipt_data, без фильтра по электроэнергии.
- PostgreSQL 18 работает в Docker на Debian: база smart_home, схема energy. Используются energy.utility_documents, energy.utility_meter_readings и energy.utility_charges.
- SMB-папка utility-import подключена к контейнеру: /home/yaha/utility-import/incoming → /files/utility-import.
- Реализован последовательный импорт PDF: чтение → извлечение текста → локальный JavaScript-парсер → PostgreSQL → удаление конкретного PDF после успешной записи.
- Работа импорта по расписанию отдельно не настроена.

Актуальный порядок работ и подтверждённые изменения: [PLAN.md](PLAN.md). [STATUS.md](STATUS.md) содержит более ранний снимок от 30 октября 2026 и ещё не отражает разделение агентов. JSON-экспорты в workflows не обновляются этим коммитом; финальные экспорты после ручных изменений нужно зафиксировать отдельно.

## Работающая архитектура

```text
Общий чат → My workflow (оркестратор)
  ├─ Call 'Agent energy' → Agent energy
  │   ├─ HA Read energy context → текущие электрические показатели
  │   └─ Energy History → HA_EnergyHistory → история датчиков
  └─ uk_agent → Агент УК
      └─ uk_receipt_context → УК — Контекст квитанций
          └─ PostgreSQL → весь сохранённый результат парсера

Windows → SMB → входная папка → n8n
  → PDF → текст → локальный парсер → PostgreSQL
  → удаление конкретного PDF после успешной записи
```

HA Read context через MCP остаётся отдельным workflow. Ветка Webhook для Алисы не объявляется подключённой к новому диалогу этим изменением.

## Разделение ответственности

### Агент УК

Единственный профильный агент по всем квитанциям ЖКХ, включая электричество. Это помощник владельца, а не представитель УК. Использует сохранённые услуги, показания, объёмы, применённые ставки, начисления, перерасчёты, льготы, пени, итоги и примечания. Другие сведения сообщает только при их наличии в сохранённых данных. Самостоятельно не выполняет платежи, не отправляет обращения, не меняет БД и не управляет устройствами.

### Энергетический агент

Работает только с электрическими данными HA: мощностью, энергией, напряжением, током, историей датчиков и домашними нагрузками. Не читает квитанции и не получает извлечённые из них сведения напрямую, от агента УК или через оркестратор. Источник ставок для расчёта стоимости пока не согласован; расчёт стоимости не объявляется реализованным.

### Оркестратор

Вопросы о квитанциях направляет агенту УК, а о нагрузках HA — энергетическому агенту. В смешанном запросе формирует независимые задачи без передачи сведений квитанций энергетическому агенту и сопоставляет ответы на своём уровне. Не приравнивает расход отдельных нагрузок к общему расходу квартиры и не смешивает несовместимые периоды и единицы.

Ключи памяти: energy:ha:v2:<sessionId>, uk:v1:<sessionId>, orchestrator:uk-energy:v2:<sessionId>. Разделение ключей исключает использование прежнего ключа истории новой ролью, но не удаляет старую память. Ограничения промптов не являются техническим фильтром содержимого.

## Ограничения данных

- Текущий контекст группирует power, energy, voltage и current по помещениям и устройствам. Нечисловое состояние не считается нулём.
- История HA: один sensor за вызов, даты с часовым поясом, максимум 7 суток. completeness=not_verified не подтверждает полноту. По прежнему сообщению владельца доступна история примерно за месяц; долгосрочный архив сырых показаний HA в PostgreSQL остаётся отложенным.
- Контекст квитанций возвращает сохранённый результат парсера, а не полный текст PDF. Полнота всех разделов и правильность всех вариантов PDF не подтверждены; отсутствие поля или null не означает ноль.
- Показания, расход, начислено и к оплате — разные величины. Индивидуальное потребление, общее имущество и содержание жилья разделяются. Итоги не складываются повторно с составляющими; детализация перерасчётов не учитывается дважды.
- billing_month не доказывает точный интервал потребления. Неизвестные даты остаются неизвестными.
- Ставка квитанции — ставка, применённая в документе, а не подтверждение действующего тарифа, срока действия или расписания зон. Отдельный тарифный справочник не создаём. Расписание Т1–Т3 для аналитики требует проверки по официальному источнику.
- Статусы контекста: found, not_found, multiple_documents. Отсутствие документа не означает нулевые начисления; несколько документов не выбираются и не суммируются автоматически.
- Успешный импорт не является независимой проверкой парсинга или обоснованности начислений УК.

## Импорт PDF и хранение

Сохраняем согласованный упрощённый процесс без дедупликации, промежуточного подтверждения, автоматических арифметических проверок и сводного отчёта. Ошибка до записи не должна приводить к удалению PDF. Ошибка удаления может оставить уже записанный документ и файл; повторный импорт способен создать дубль. Архив исходных PDF и журнал ошибок вне PostgreSQL без отдельного согласования не добавляем.

Чтение полного payload снимает электрический фильтр, но не восстанавливает пропущенные при импорте поля. Полноту задолженности, аванса, оплат, сроков и других разделов предстоит развивать отдельно. Это обновление документации не меняет парсер или данные БД и не подтверждает полноту загрузки архива квитанций.

## Безопасность

Не публиковать токены, пароли, оригиналы квитанций, лицевые счета, ФИО, адреса и закреплённые персональные результаты. Гостевой SMB доступен только в доверенной локальной сети; подключившиеся клиенты могут менять и удалять файлы. Не публиковать SMB в интернет. Изменения гостевого входа и SMB-подписи Windows имеют клиентский масштаб.

Execute Command включён для удаления PDF и расширяет полномочия workflow. Удалять только конкретный проверенный путь внутри входной папки; файловое ограничение n8n не является песочницей shell-команд. Существующие экспорты с локальными адресами и служебными ссылками не считать прошедшими полный аудит.

Автоматическое удаление успешно импортированного PDF согласовано отдельно. Покупки, установка ПО и оборудования, настройки, платежи, обращения и управление устройствами требуют отдельного согласования владельца.
