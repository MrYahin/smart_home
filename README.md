# Smart Home

Многоагентная система умного дома на базе Home Assistant и n8n. Цель — экономить деньги без снижения комфорта и улучшать условия проживания.

## Правила работы — читать первым

Перед разработкой прочитать [AGENTS.md](AGENTS.md). Пользователь решает, что и когда публикуется. Запись ассистентом в GitHub допускается только по прямой просьбе на конкретное действие и после согласования изменений. Настройку n8n ведём пошагово: владелец сам создаёт и изменяет узлы по инструкциям.

## Архитектура

```text
Чат n8n → My workflow (оркестратор)
  ├─ Call 'Agent energy' → Agent energy
  │   ├─ HA Read energy context → текущие электрические показатели
  │   └─ Energy History → HA_EnergyHistory → история датчиков
  └─ uk_agent → Агент УК
      └─ uk_receipt_context → УК — Контекст квитанций
          └─ PostgreSQL → сохранённый результат парсера

Windows → SMB → входная папка → n8n
  → PDF → текст → локальный парсер → PostgreSQL
  → удаление конкретного PDF после успешной записи

Следующий этап, ещё не подключён:
существующий диалог оркестратора → подтверждаемый профиль владельца
  → owner_profile.preferences
```

HA Read context через MCP остаётся отдельным workflow. В предоставленном экспорте Webhook Алисы соединён с фиксированным ответом, а не с AI Agent.

## Разделение ответственности

- Агент УК — единственный профильный агент по всем квитанциям ЖКХ, включая электричество; помощник владельца, а не представитель УК. Сообщает только сохранённые документальные сведения. Не выполняет платежи, обращения, изменение БД или управление устройствами.
- Энергетический агент работает с электрическими данными HA: мощностью, энергией, напряжением, током, историей и нагрузками. Не получает сведения квитанций напрямую, через агента УК или оркестратор. Источник ставок для расчёта стоимости не согласован.
- Оркестратор маршрутизирует вопросы, разделяет смешанные задачи и сопоставляет независимые ответы только при совместимости периодов, единиц и охвата. Расход отдельных нагрузок HA не равен общему расходу квартиры.

Ключи памяти: energy:ha:v2:<sessionId>, uk:v1:<sessionId>, orchestrator:uk-energy:v2:<sessionId>. Промпты и отдельные ключи не гарантируют техническую изоляцию и не удаляют прежнюю память. В разделе ответственности PLAN.md остаётся противоречащая этому разделению оговорка; без отдельного согласования её не меняем.

## Профиль владельца — подготовка

Таблица preferences содержит id, preference_key (UNIQUE), preference_value (JSONB), description и created_at. Это заготовка, а не завершённая модель подтверждений. Достаточность структуры для области, срока действия, подтверждения и управления записями ещё предстоит согласовать.

Следующая задача — расширить существующего оркестратора, не создавать второй общий чат. Выявлять предпочтения в диалоге, уточнять формулировку, область и срок, сохранять только после подтверждения; обеспечить просмотр, исправление и удаление. Предположения не считать фактами. Сохранение предпочтения не является разрешением управлять устройствами.

Тестовый workflow записи пропущен по решению владельца. Запись и чтение предпочтений через новый workflow не проверялись; подключение инструментов профиля и механизм подтверждения пока отсутствуют.

## Ограничения данных и импорта

- История HA: один sensor за вызов, максимум 7 суток; completeness=not_verified не подтверждает полноту. Ранее владелец сообщал примерно о месяце доступной истории. Долгосрочный архив сырых данных отложен. Месячные счётчики не складываются с исходными накопительными; нечисловое состояние не считается нулём.
- Контекст квитанций возвращает весь сохранённый payload, а не полный PDF. Полнота задолженности, аванса, оплат, сроков и прочих разделов не подтверждена. Отсутствующее поле или null не означает ноль.
- Показания, расход, начислено и к оплате различаются. Индивидуальное потребление, общее имущество и содержание жилья разделяются. Итоги и перерасчёты повторно не суммируются.
- Расчётный месяц не устанавливает точный период потребления. Применённая ставка не подтверждает действующий тариф или расписание зон. Отдельный тарифный справочник не создаём; расписание Т1–Т3 требует официального подтверждения.
- Статусы контекста: found, not_found, multiple_documents. Несколько документов не выбираются и не суммируются автоматически.
- Сохраняем упрощённый импорт без дедупликации, промежуточного подтверждения, автоматических арифметических проверок и сводного отчёта. Повторный импорт может создать дубль; ошибка удаления может оставить записанный документ и PDF. Ошибка до записи не должна приводить к удалению файла.
- Успешный импорт не доказывает правильность парсинга или обоснованность начислений. Архив оригиналов и журнал ошибок вне PostgreSQL без отдельного решения не добавляем.

## Дальнейшее развитие

По PLAN.md: профиль владельца → полнота контекста УК → аналитика нагрузок HA и времени по зонам → взаимодействие агентов → остальные подсистемы → ежедневные 1–3 предложения → вечернее обновление существующего HA-дашборда. Выгоду и окупаемость не выдумываем, расчёты выполняем кодом. Управление и изменения — только после отдельного согласования.

## Безопасность

Не публиковать токены, пароли, оригиналы квитанций, лицевые счета, ФИО, адреса и закреплённые персональные результаты. Экспорты содержат служебные идентификаторы и локальные ссылки; полный аудит безопасности не выполнен.

SMB utility-import: /home/yaha/utility-import/incoming → /files/utility-import. Гостевой доступ допустим только в доверенной локальной сети; клиенты могут менять и удалять файлы. Не публиковать SMB в интернет. Изменения гостевого входа и SMB-подписи Windows имеют клиентский масштаб.

Execute Command расширяет полномочия workflow. Удалять только конкретный проверенный путь внутри входной папки; файловое ограничение n8n не является песочницей shell-команд. Удаление успешно импортированного PDF согласовано отдельно. Покупки, установка ПО и оборудования, настройки, платежи, обращения и управление устройствами требуют отдельного подтверждения.
